# Publish the Demo on Render

This configuration publishes a simulation with seven fictional participants and has no registry or legal validity. Meeting, document, and real institutional sign-in integrations are not connected. The environment has not been validated for 8,000 participants.

## 1. Push the changes to GitHub

In GitHub Desktop, commit the changes and select **Push origin**. If the repository has not yet been published, choose **Publish repository**.

On the repository page, confirm that `render.yaml`, `Dockerfile`, and `deploy/start.sh` are at the repository root. The expected root is the application folder, with `backend` and `frontend` directly beneath it, not the entire parent workspace folder.

## 2. Create the service from the Blueprint

1. Sign in at https://dashboard.render.com/ with your GitHub account.
2. Select **New → Blueprint**.
3. Connect the repository. If it is private, grant Render access to that repository through the GitHub integration.
4. Select the **main** branch and keep `render.yaml` as the Blueprint Path.
5. Give the Blueprint a name, for example `votria-demo`.
6. Set a dedicated demo access password of at least 16 characters. Prefer a long passphrase or a password generated by a password manager. Do not commit it to GitHub; share it only with the test group.
7. Enter the institution for this deployment: `VOTRIA_INSTITUTION_NAME` (the name shown on the sign-in screen) and `VOTRIA_ALLOWED_EMAIL_DOMAIN` (for example, `example.org`). The fictional accounts will use that domain. For a generic demo, leave the domain blank or use `demo.votria.test`.
8. Review the resources and prices shown: the supplied configuration defines one Web Service and one PostgreSQL database, both using the **Free** plan.
9. Confirm with **Deploy Blueprint / Apply**, depending on the button shown by Render.

The deployment generates a random internal key, connects to the database over the private network, builds the interface, and applies migrations. On startup, it loads fictional data only when the data does not already exist. No manual commands or separate website configuration are needed.

Do not select a paid plan without checking the displayed price. Plan names and availability can change; if Free is unavailable, review the selection before confirming.

## 3. Open and test

Open the Web Service created by the Blueprint. Wait for the **Live** status, then open the HTTPS URL shown by Render, usually ending in `.onrender.com`.

Enter the demo access password and select a fictional participant. Each participant should use a separate browser profile and a distinct fictional identity. Switching identities ends the previous participant's attendance; tabs in the same profile share one identity.

Suggested small-group walkthrough:

1. Each participant selects a different fictional identity and confirms attendance.
2. Before the meeting is installed, Carla creates a proxy authorization for Diego. Carla retrieves the code from her own test inbox and shares it with Diego, who accepts it.
3. Ana, acting as chair, confirms attendance and installs the meeting in the second call, or in the first call if there are five personally present participants.
4. Ana opens an ordinary agenda item. Participants vote and try the speaking-request flow.
5. Ana closes the vote. Review the roll-call votes, YES > NO rule, abstentions, and outcome.
6. Ana finalizes the meeting and downloads the JSON draft minutes. This is a demonstration result only.

The rehearsal uses one shared meeting. Votes and history are not cleared by restarting the service or deploying an update. After finalizing, the chair can start a new demo. History remains in the previous meeting. Connected participants are moved to the new demo by the page's periodic refresh; reload the page if needed. Everyone must confirm attendance and create proxy authorizations again. The access password remains unchanged.

## 4. Share access

Send the HTTPS URL and password to the group through a private channel you choose. The password provides access to all fictional profiles, including the chair profile; it is not authentication for real members. Do not use real accounts, documents, or personal data in this environment.

## Updates, limits, and troubleshooting

To update the code, commit and push the changes. Check the new deployment in Render. Preserve the application's secret key: it also protects codes in the test inbox. Changing it invalidates sessions and prevents reading existing codes.

The Free service pauses after 15 minutes without traffic and may take about a minute to start again. The Free PostgreSQL database expires after 30 days and has no backups. To retain history longer, select a paid database before expiration and establish backups. The final price is the one displayed by Render.

If an error occurs, open **Logs** for the service. The access password must be at least 16 characters; a connection failure requires checking the database; a build error must be fixed before sharing the link. Do not enable DEBUG to work around errors. After changing the password, restart the service. If existing authenticated sessions must be revoked, use an administrative procedure: changing the password alone does not end existing sessions.

The real deployment, Docker/Linux build, and PostgreSQL concurrency still need to be checked during the first deployment. Preparing these files locally does not create a public URL.
